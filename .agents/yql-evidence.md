# YQL implementation evidence

These source references support the analyzer's documented [schema migration coverage](../docs/compatibility.md#schema-migration-coverage). They record the implementation examined, not a claim about the latest YQL revision.

YQL main at `d62403dadf7588c33d2d0a61296a157b61163d52` explicitly handles [`DROP TABLE IF EXISTS` through `missingOk`](https://github.com/ydb-platform/ydb/blob/d62403dadf7588c33d2d0a61296a157b61163d52/yql/essentials/sql/v1/translation/sql_query.cpp#L575) and [rejects combining RENAME TO with other ALTER actions](https://github.com/ydb-platform/ydb/blob/d62403dadf7588c33d2d0a61296a157b61163d52/yql/essentials/sql/v1/translation/sql_query.cpp#L2399).

## AS_TABLE and DML projections

The [AS_TABLE reference](https://ydb.tech/docs/en/yql/reference/syntax/select/from_as_table) requires explicit column lists on both INSERT and SELECT sides when specifying target columns. AS_TABLE source column order is not guaranteed by its struct declaration. The analyzer therefore rejects wildcard INSERT/UPSERT SELECT projections with an explicit target list. Struct equality compares named field sets independently of declaration order while retaining source order for generated representations. See [expression type rules](https://ydb.tech/docs/en/yql/reference/syntax/expressions).

On 2026-09-15, local YDB (`ydbplatform/local-ydb:nightly`, image digest `sha256:16fc066d4944ce7b4bf73ecd8732dcc077e2b8303075f4470a616113ad381af4`) confirmed that both INSERT and UPSERT with an explicit target list map explicit SELECT expressions by position, including when their aliases are reversed. The server emitted alias-mismatch warnings but stored the first projected value in the first listed target column. This evidence is specific to the explicit-target form: it does not establish positional matching for statements without a target list.

Review follow-up on the same image confirmed contextual NULL typing for DML SELECT sources: `INSERT INTO ... (nullable_column) SELECT NULL` and `UPDATE ... ON SELECT NULL AS nullable_column` both succeeded, and the selected row contained SQL NULL. The analyzer therefore accepts the unresolved `Null` expression type only when the destination column is optional; required columns and primary keys remain incompatible.

UPDATE/DELETE ON SELECT instead validate the source's named columns and require the complete primary key; their star expansion is used only for named matching, never to infer Struct field order. `TestLiveYDBTypedDML` executes generated Go code for both native and database/sql adapters, including reordered AS_TABLE fields, partial updates, absent keys, filters, empty lists and a standalone Struct key. It passed against the same local image on 2026-09-15 with SDK v3.151.1.

On 2026-09-22, `TestLiveYDBTypedDML` passed against `ydbplatform/local-ydb:26.3.1.8` (`sha256:d0c402700a78cbb8a45b35ffd4be69f5fcb241361ffe3fa5c8846d56b5872294`) using Go SDK v3.151.1 through both native Query SDK and database/sql adapters, sequentially in an isolated disposable container. The generated queries confirmed that INSERT/UPSERT without a target column list map SELECT results by name, including reordered fields, explicit aliases, bare `*`, and `alias.*` combined with computed columns. All wildcards were expanded by sqlc-ydb before execution. The same fixture accepted trailing commas in List<Struct> declarations, preserved omitted nullable UPSERT columns on existing rows, accepted nil and empty batches, and executed a named UPSERT with contextual NULL and RETURNING.

The same server rejected a named UPSERT that omitted a NOT NULL non-key column, even when the destination row existed and when the source batch was empty: `Missing not null column in input: attributes. All not null columns should be initialized`. The named-write analyzer therefore requires every non-generated NOT NULL column in addition to non-generated primary-key columns. Nullable-column preservation must not be generalized to required columns. Generated serial-key omission is covered by the analyzer's existing serial contract and unit regressions; this named-write live fixture does not exercise serial columns.

On 2026-09-23, the expanded `TestLiveYDBTypedDML` passed on the same pinned `ydbplatform/local-ydb:26.3.1.8` image. Both generated Go adapters executed an explicit-target UPSERT with reordered target columns and deliberately mismatched source aliases; RETURNING and a subsequent read confirmed positional assignment and preservation of an omitted nullable column. Raw Query SDK probes rejected explicit-target INSERT and UPSERT that omitted either the required `attributes` column or the non-generated `owner_hash` key, for both populated and empty SELECT sources. The fixture also retained its generated positional INSERT coverage. Offline analysis now applies the same required-column policy to the named and positional forms; serial-key omission remains covered by analyzer regressions rather than this live fixture.

## Secondary indexes

The [index DDL reference](https://ydb.tech/docs/en/yql/reference/syntax/create_table/secondary_index) defines ordinary GLOBAL SYNC/ASYNC keys and covering columns; the [VIEW reference](https://ydb.tech/docs/en/yql/reference/syntax/select/secondary_index) selects an index on a base-table source, including aliases and joins. Indexes retain base-table column types. These require index metadata in the existing table catalog for name validation and schema drift; no separate index relation or runtime transaction policy is introduced.

On 2026-09-23, `TestLiveYDBIndexes`, `TestLiveYDBIndexMetadata` and the authors Go acceptance test passed sequentially against `ydbplatform/local-ydb:26.3.1.8` (`sha256:d0c402700a78cbb8a45b35ffd4be69f5fcb241361ffe3fa5c8846d56b5872294`) in an isolated disposable container. Both generated Go adapters using SDK v3.151.1 executed ordinary and covering index reads, nullable and empty results, and INSERT/UPSERT SELECT from indexed sources. Real DescribeTable data preserved sync/async kind, ordered keys and covering columns; offline analysis, schema-free discovery and local-schema checks agreed, and index drift was detected. Covering-column order was intentionally ignored.

The same native Go fixture confirmed that the default transaction mode rejects async-index reads with a StaleRO diagnostic. Passing `query.WithTxControl(query.StaleReadOnlyTxControl())` succeeded after a bounded wait for index convergence. This establishes the explicit native Go recipe, not automatic consistency selection for every runtime. The server also rejected COVER entries that overlap the index key or primary key, and rejected DROP COLUMN when an index keys or covers that column. Offline diagnostics retain these constraints.

The authors jOOQ acceptance harness executed both the DSL ordinary-index query and the explicitly declared covering-index query with table mapping, against jOOQ 3.21.0, YDB dialect 2.0.0 and JDBC 2.4.1. Both queries retained VIEW selection, nullable payloads and empty-result behavior. The generator's SDK checks compile and render the same query parts with the pinned dependencies.

## Function contracts

On 2026-09-15, local YDB accepted `SELECT "plain"u = "plain"` and `CAST("101" AS Decimal(22,9)) > 100`, both returning true. It rejected `SELECT 1ul IN (AsList(1ul,2ul))` with `Can't compare Uint64 with List<Uint64>`. This supports keeping parenthesized List operands distinct from the unparenthesized `IN $ids` form.

`TestLiveYDBSemanticTypes` compares the analyzer's result types against server metadata. On the same local image it confirmed all 21 shipped Digest functions with plain and optional inputs, including omitted, NULL and named seeds where supported. A seed's optionality does not itself make the return type optional; AutoMap on the input does. These are offline signatures, not UDF implementations. User-defined contracts belong to one SQL configuration entry and do not execute or install code.

The existing collection predicate is covered by the [dictionary functions](https://ydb.tech/docs/en/yql/reference/builtins/dict) and [Yson conversion](https://ydb.tech/docs/en/yql/reference/udf/list/yson) contracts. Live `TypeOf` probes confirmed that `Yson::ConvertToStringList` with nullable Json or Yson input returns a required `List<String>`, whereas `ToSet` of an optional list and `SetIsDisjoint` with optional collection inputs retain optionality. Resource-valued Yson overloads remain outside this implementation.

Review follow-up on the same image confirmed that optional dictionary keys are valid: `ToSet(AsList(CAST("a" AS String?), CAST(NULL AS String?)))` has type `Set<String?>`, and `SetIsDisjoint` against a list containing the same NULL key returns false. Additional `ToSet` probes accepted `Decimal(22,9)`, `DyNumber`, `Float`, `Optional<Tuple<String,Uint64>>`, and nested tuple keys while rejecting `Json`, `JsonDocument`, and `Yson` as not hashable and equatable. Optional key elements must not be confused with an optional outer collection. Also, unparenthesized `NOT a = b` applies NOT to `a` before comparison: the server rejects numeric `a` with an expected-Bool diagnostic. Tests retain that rejection while covering parenthesized Boolean predicates, BETWEEN and LIKE.

## Computed DML values

On 2026-09-22, `ydbplatform/local-ydb:26.3.1.8` passed `TestLiveYDBComputedDML` with Go SDK 3.151.1 (native Query SDK and database/sql) and Python SDK 3.29.7. The generated APIs executed INSERT constants and NULL, UPDATE target-column arithmetic with precedence and COALESCE, nullable resets, UPSERT arithmetic, RETURNING, read-your-writes and rollback. Sixteen concurrent increments per adapter ran inside the SDK's retrying transaction boundary; each committed RETURNING value was unique and the final total included every increment. Connected EXPLAIN validation produced the same generated files as offline analysis without executing the writes.

On the same image, `TestLiveYDBSemanticTypes` compared arithmetic results with server metadata: all primitive integer widths, mixed signed/unsigned operands, integer/Float and Float/Double combinations, nested parentheses and optional operands matched the shared resolver. Integer arithmetic retains its operand/common width; it is not automatically promoted to Int64. The computed DML execution test also confirms Int32 constants can be assigned to Int64 destinations. Assignment narrowing and other value-dependent conversions remain deliberately unsupported; unresolved NULL arithmetic, Decimal and temporal operands need separate rules.

Review follow-up on 2026-09-22 confirmed required/optional Uint32-to-Int64 assignments in INSERT/UPSERT SELECT, Uint32-to-Uint64 key widening in UPDATE/DELETE ON SELECT, and Boolean/nullable Boolean assignments from comparisons. YDB rejected duplicate SET targets with `Duplicated member: value`; offline analysis now diagnoses the duplicate before generation. The generated computed-DML fixture also executes comparison assignments and SELECT-backed widening through both Go adapters and Python.
