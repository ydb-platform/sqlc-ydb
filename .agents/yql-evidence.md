# YQL implementation evidence

These source references support the analyzer's documented [schema migration coverage](../docs/compatibility.md#schema-migration-coverage). They record the implementation examined, not a claim about the latest YQL revision.

YQL main at `d62403dadf7588c33d2d0a61296a157b61163d52` explicitly handles [`DROP TABLE IF EXISTS` through `missingOk`](https://github.com/ydb-platform/ydb/blob/d62403dadf7588c33d2d0a61296a157b61163d52/yql/essentials/sql/v1/translation/sql_query.cpp#L575) and [rejects combining RENAME TO with other ALTER actions](https://github.com/ydb-platform/ydb/blob/d62403dadf7588c33d2d0a61296a157b61163d52/yql/essentials/sql/v1/translation/sql_query.cpp#L2399).

## AS_TABLE and DML projections

The [AS_TABLE reference](https://ydb.tech/docs/en/yql/reference/syntax/select/from_as_table) requires explicit column lists on both INSERT and SELECT sides when specifying target columns. AS_TABLE source column order is not guaranteed by its struct declaration. The analyzer therefore rejects wildcard INSERT/UPSERT SELECT projections with an explicit target list. Struct equality compares named field sets independently of declaration order while retaining source order for generated representations. See [expression type rules](https://ydb.tech/docs/en/yql/reference/syntax/expressions).

On 2026-09-15, local YDB (`ydbplatform/local-ydb:nightly`, image digest `sha256:16fc066d4944ce7b4bf73ecd8732dcc077e2b8303075f4470a616113ad381af4`) confirmed that both INSERT and UPSERT with an explicit target list map explicit SELECT expressions by position, including when their aliases are reversed. The server emitted alias-mismatch warnings but stored the first projected value in the first listed target column. This evidence is specific to the explicit-target form: it does not establish positional matching for statements without a target list.

Review follow-up on the same image confirmed contextual NULL typing for DML SELECT sources: `INSERT INTO ... (nullable_column) SELECT NULL` and `UPDATE ... ON SELECT NULL AS nullable_column` both succeeded, and the selected row contained SQL NULL. The analyzer therefore accepts the unresolved `Null` expression type only when the destination column is optional; required columns and primary keys remain incompatible.

UPDATE/DELETE ON SELECT instead validate the source's named columns and require the complete primary key; their star expansion is used only for named matching, never to infer Struct field order. `TestLiveYDBTypedDML` executes generated Go code for both native and database/sql adapters, including reordered AS_TABLE fields, partial updates, absent keys, filters, empty lists and a standalone Struct key. It passed against the same local image on 2026-09-15 with SDK v3.151.1.

On 2026-09-22, `TestLiveYDBTypedDML` passed against `ydbplatform/local-ydb:26.3.1.8` (`sha256:d0c402700a78cbb8a45b35ffd4be69f5fcb241361ffe3fa5c8846d56b5872294`) using Go SDK v3.151.1 through both native Query SDK and database/sql adapters, sequentially in an isolated disposable container. The generated queries confirmed that INSERT/UPSERT without a target column list map SELECT results by name, including reordered fields, explicit aliases, bare `*`, and `alias.*` combined with computed columns. All wildcards were expanded by sqlc-ydb before execution. The same fixture accepted trailing commas in List<Struct> declarations, preserved omitted nullable UPSERT columns on existing rows, accepted nil and empty batches, and executed a named UPSERT with contextual NULL and RETURNING.

The same server rejected a named UPSERT that omitted a NOT NULL non-key column, even when the destination row existed and when the source batch was empty: `Missing not null column in input: attributes. All not null columns should be initialized`. The named-write analyzer therefore requires every non-generated NOT NULL column in addition to non-generated primary-key columns. Nullable-column preservation must not be generalized to required columns. Generated serial-key omission is covered by the analyzer's existing serial contract and unit regressions; this named-write live fixture does not exercise serial columns.

On 2026-09-23, the expanded `TestLiveYDBTypedDML` passed on the same pinned `ydbplatform/local-ydb:26.3.1.8` image. Both generated Go adapters executed an explicit-target UPSERT with reordered target columns and deliberately mismatched source aliases; RETURNING and a subsequent read confirmed positional assignment and preservation of an omitted nullable column. Raw Query SDK probes rejected explicit-target INSERT and UPSERT that omitted either the required `attributes` column or the non-generated `owner_hash` key, for both populated and empty SELECT sources. The fixture also retained its generated positional INSERT coverage. Offline analysis now applies the same required-column policy to the named and positional forms; serial-key omission remains covered by analyzer regressions rather than this live fixture.

## Secondary indexes

The [index DDL reference](https://ydb.tech/docs/en/yql/reference/syntax/create_table/secondary_index) defines ordinary GLOBAL SYNC/ASYNC keys and covering columns; the [VIEW reference](https://ydb.tech/docs/en/yql/reference/syntax/select/secondary_index) selects an index on a base-table source, including aliases and joins. Indexes retain base-table column types. These require index metadata in the existing table catalog for name validation and schema drift; no separate index relation or runtime transaction policy is introduced.

On 2026-09-23, `TestLiveYDBIndexes`, `TestLiveYDBIndexMetadata` and the authors Go acceptance test passed sequentially against `ydbplatform/local-ydb:26.3.1.8` (`sha256:d0c402700a78cbb8a45b35ffd4be69f5fcb241361ffe3fa5c8846d56b5872294`) in an isolated disposable container. Both generated Go adapters using SDK v3.151.1 executed ordinary and covering index reads, nullable and empty results, and INSERT/UPSERT SELECT from indexed sources. Real DescribeTable data preserved sync/async kind, ordered keys and covering columns; offline analysis, schema-free discovery and local-schema checks agreed, and index drift was detected. Covering-column order was intentionally ignored.

The same native Go fixture confirmed that the default transaction mode rejects async-index reads with a StaleRO diagnostic. Passing `query.WithTxControl(query.StaleReadOnlyTxControl())` succeeded after a bounded wait for index convergence. This establishes the explicit native Go recipe, not automatic consistency selection for every runtime. The server also rejected COVER entries that overlap the index key or primary key, and rejected DROP COLUMN when an index keys or covers that column. Offline diagnostics retain these constraints.

The authors jOOQ acceptance harness executed both the DSL ordinary-index query and the explicitly declared covering-index query with table mapping, against jOOQ 3.21.0, YDB dialect 2.0.0 and JDBC 2.4.1. Both queries retained VIEW selection, nullable payloads and empty-result behavior. The generator's SDK checks compile and render the same query parts with the pinned dependencies.

## Function contracts

On 2026-09-15, local YDB accepted `SELECT "plain"u = "plain"` and `CAST("101" AS Decimal(22,9)) > 100`, both returning true. It rejected `SELECT 1ul IN (AsList(1ul,2ul))` with `Can't compare Uint64 with List<Uint64>`. This supports keeping parenthesized List operands distinct from the unparenthesized `IN $ids` form.

`TestLiveYDBSemanticTypes` compares the analyzer's result types against server metadata. On the same local image it confirmed all 21 shipped Digest functions with plain and optional inputs, including omitted, NULL and named seeds where supported. A seed's optionality does not itself make the return type optional; AutoMap on the input does. These are offline signatures, not UDF implementations. User-defined contracts belong to one SQL configuration entry and do not execute or install code.

The existing collection predicate is covered by the [dictionary functions](https://ydb.tech/docs/en/yql/reference/builtins/dict) and [Yson conversion](https://ydb.tech/docs/en/yql/reference/udf/list/yson) contracts. Live `TypeOf` probes confirmed that `Yson::ConvertToStringList` with nullable Json or Yson input returns a required `List<String>`, whereas `ToSet` of an optional list and `SetIsDisjoint` with optional collection inputs retain optionality. Resource-valued Yson overloads remain outside this implementation.

Review follow-up on the same image confirmed that optional dictionary keys are valid: `ToSet(AsList(CAST("a" AS String?), CAST(NULL AS String?)))` has type `Set<String?>`, and `SetIsDisjoint` against a list containing the same NULL key returns false. Additional `ToSet` probes accepted `Decimal(22,9)`, `DyNumber`, `Float`, `Optional<Tuple<String,Uint64>>`, and nested tuple keys while rejecting `Json`, `JsonDocument`, and `Yson` as not hashable and equatable. Optional key elements must not be confused with an optional outer collection. Also, unparenthesized `NOT a = b` applies NOT to `a` before comparison: the server rejects numeric `a` with an expected-Bool diagnostic. Tests retain that rejection while covering parenthesized Boolean predicates, BETWEEN and LIKE.

## Computed DML values

On 2026-09-22, `ydbplatform/local-ydb:26.3.1.8` passed `TestLiveYDBComputedDML` with Go SDK 3.151.1 (native Query SDK and database/sql) and Python SDK 3.29.7. The generated APIs executed INSERT constants and NULL, UPDATE target-column arithmetic with precedence and COALESCE, nullable resets, UPSERT arithmetic, RETURNING, read-your-writes and rollback. Sixteen concurrent increments per adapter ran inside the SDK's retrying transaction boundary; each committed RETURNING value was unique and the final total included every increment. Connected EXPLAIN validation produced the same generated files as offline analysis without executing the writes.

On the same image, `TestLiveYDBSemanticTypes` compared arithmetic results with server metadata: all primitive integer widths, mixed signed/unsigned operands, integer/Float and Float/Double combinations, nested parentheses and optional operands matched the shared resolver. Integer arithmetic retains its operand/common width; it is not automatically promoted to Int64. The computed DML execution test also confirms Int32 constants can be assigned to Int64 destinations. Assignment narrowing and other value-dependent conversions remain deliberately unsupported; unresolved NULL arithmetic, Decimal and temporal operands need separate rules.

Review follow-up on 2026-09-22 confirmed required/optional Uint32-to-Int64 assignments in INSERT/UPSERT SELECT, Uint32-to-Uint64 key widening in UPDATE/DELETE ON SELECT, and Boolean/nullable Boolean assignments from comparisons. YDB rejected duplicate SET targets with `Duplicated member: value`; offline analysis now diagnoses the duplicate before generation. The generated computed-DML fixture also executes comparison assignments and SELECT-backed widening through both Go adapters and Python.

## TablePathPrefix

The [TablePathPrefix reference](https://ydb.tech/docs/en/yql/reference/syntax/pragma#tablepathprefix) describes path concatenation and absolute-table-path bypass. Sequential probes on 2026-09-23 against `ydbplatform/local-ydb:26.3.1.16` (`sha256:32687d3bc4b7a3e4200e2142800e5fc2e91d48ba46160ea094e9f1ce56794c12`) observed two version-specific behaviors: an explicit prefix is rooted at the server root, not the connection's database, and the last prefix affects the whole request, including earlier SELECT/CREATE statements. On that image, ordinary table references without a pragma retain their database-relative behavior, while an empty or relative prefix does not mean the connection's database root. The compiler contract accepts one nonempty absolute prefix per named query/schema source and diagnoses conflicting or late declarations.

Source review on 2026-09-23 covered open, unmerged YDB PRs [#53874](https://github.com/ydb-platform/ydb/pull/53874) at `51336f136ced691df04bbf5389d998d4e37742d8` and [#53875](https://github.com/ydb-platform/ydb/pull/53875) at `4c54358a95a636ffeb26ce6da1ade538814b6d41`. The former resolves relative prefix values against the configured database path for the local Kikimr service when that database path is absolute; it preserves absolute prefix values. The latter captures table-reference prefix context during parsing so later pragmas do not retroactively change earlier references. These are source-analysis findings, not execution results from a server containing those changes. The supported leading absolute prefix and jOOQ relative table mappings retain the same meaning under both models. Relative prefix values and statement-local prefix changes remain outside sqlc-ydb's current coverage.

The 26.3.1.16 probes also accepted dot/parent/slash normalization, absolute table-path bypass, prefixed CREATE/ALTER/RENAME/DROP, ordinary quoted string literals and hexadecimal, Unicode and octal slash escapes. Doubled SQL quotes and a Utf8 suffix were rejected for pragma literals. A declared SQL alias hides the original table qualifier; source `users AS u` accepts `u.id` but rejects `users.id`, `users.*` and the resolved physical path as qualifiers. The analyzer retains authored relation aliases independently of resolved catalog identity.

The review-followup probe on the same image confirmed that aliases are case-sensitive. With fixture rows `(id, link) = (1, 0), (2, 1)`, a self-join with aliases `r` and `R` and condition `r.id = R.link` returned `(r.id, R.id) = (1, 2)`. A projection of `r.ID` was rejected with `Member not found: ID`. `TestColumnBindingsPreserveAliasCase` verifies distinct resolved table, alias and type bindings in SELECT projections, JOIN conditions and WHERE predicates, with and without a prefix.

`TestLiveYDBTablePathPrefix` passed on that image using generated native Go/database/sql clients with SDK v3.151.1 and jOOQ 3.21.0, dialect 2.0.0 and JDBC 2.4.1. It checked two namespaces, matching offline/discovered/local-schema metadata, per-namespace drift, writes, VIEW reads, absolute-path bypass and cross-namespace UPSERT SELECT. jOOQ execution covered inferred and declared parameters, relative/absolute RenderMapping outputs, maximum Uint64, DELETE RETURNING and a declared self-select UPSERT. The tests created and removed only their own tables; they did not restart the shared local-ydb service. CI separately runs the public suite on its pinned stable image and nightly.

## Integer aliases and pagination

On 2026-09-23, `TestLiveYDBIntegerLimits` passed sequentially through generated native Go and database/sql clients using Go SDK v3.151.1 against `ydbplatform/local-ydb:26.3.1.8` (`sha256:d0c402700a78cbb8a45b35ffd4be69f5fcb241361ffe3fa5c8846d56b5872294`). DECLARE bindings and actual table-column metadata confirmed `TinyInt` → `Int8`, `SmallInt` → `Int16`, `Int`/`Integer` → `Int32`, and `BigInt` → `Int64`. Alias bindings preserved signed boundary values. The analyzer canonicalizes these names; generated SQL retains their original spelling.

The same fixture executed LIMIT and OFFSET with required and optional `Int8`, `Int16`, `Int32`, `Uint8`, `Uint16`, `Uint32`, and `Uint64` parameters. It checked zero and positive counts, NULL counts, negative signed parameters, maximum Uint64 values, and `LIMIT offset, count` ordering. NULL LIMIT returned all fixture rows and NULL OFFSET skipped none. A negative limit with offset zero returned all rows; a negative offset returned none. The separate `TestAuthorsPagination` confirmed an Int32 limit of -1 with a Uint32 offset of one returned no rows. These are server expression semantics, not a client-side nonnegative, saturation or unsigned-conversion policy. The authors jOOQ live test also passed with jOOQ 3.21.0, YDB dialect 2.0.0 and JDBC 2.4.1, executing the original `DECLARE ... AS Int` and a Uint32 offset above the signed Int32 range.

Both EXPLAIN and execution rejected Int64, optional Int64, Double, Bool and Utf8 count expressions and an overflowing Uint64 literal. Positive Int64 literals, including `9223372036854775807l`, executed successfully; `CAST(1 AS Int64)` was rejected. Separate raw probes also accepted a local Int64 literal binding and direct negative integer literals, which remain outside the analyzer's current expression/provenance subset. The offline diagnostics document that narrower subset rather than attributing those restrictions to YDB.

A bounded raw probe of the authors-shaped query with an Int32 page size of 1 or 2 and Uint32 offset `4294967295` reached the four-second request deadline; the first generated test attempt reached its 90-second context deadline. The same raw query returned immediately at offset `2147483648` and `1000`, and at maximum Int32 page size with offset zero. This observation does not establish a server root cause or a universal timeout boundary. The executable example tests use an offset above the signed Int32 range that completed successfully; the generator preserves the full Uint32 binding range without a compensating cast or hidden limit.

## Shared expressions and implicit result names

The shared-expression implementation was checked on 2026-09-23 against YDB commit `1415fed8104201c5e973dd8bbf12c71c6b1ed8b9`. Its [basic built-ins](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/ydb/docs/en/core/yql/reference/builtins/basic.md), [aggregate functions](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/ydb/docs/en/core/yql/reference/builtins/aggregation.md) and [CAST reference](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/ydb/docs/en/core/yql/reference/types/cast.md) define the documented forms. `CoalesceWrapper`, `DataGeneratorWrapper` and `CurrentTzWrapper` in [type_ann_core.cpp](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/yql/essentials/core/type_ann/type_ann_core.cpp#L6171) supply the value-dependent/common-type and optionality rules. SQL translation [requires at least one dependency argument for Random, RandomNumber and RandomUuid](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/yql/essentials/sql/v1/translation/builtin.cpp#L3448), despite the lower-level data-generator wrapper accepting zero arguments.

For unnamed SELECT outputs, [core type annotation](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/yql/essentials/core/type_ann/type_ann_core.cpp#L13084) reserves named outputs before allocating `columnN` from the projection item's zero-based ordinal and incrementing past collisions. [SELECT translation](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/yql/essentials/sql/v1/translation/select.cpp#L2351) distinguishes pure column references from computed expressions. The [result provider](https://github.com/ydb-platform/ydb/blob/1415fed8104201c5e973dd8bbf12c71c6b1ed8b9/yql/essentials/providers/result/provider/yql_result_provider.cpp#L164) drops an unusable original column-order hint; collision probes then observed lexical struct-member order on the wire. The analyzer implements these rules without copying upstream source.

Wildcard expansion can change projection ordinals, so shared normalization inserts explicit aliases preserving the original implicit names alongside its existing star replacement. This is necessary for SQL such as `SELECT t.*, 1 FROM t ORDER BY column1`: expanding a two-column table must not silently rename the expression to `column2`. Reanalysis of normalized SQL provides the final output order. Queries without wildcard expansion retain their authored SQL, including unnamed expressions.

On the same server, `SELECT id > 0ul AS id ... ORDER BY id = $p` compared the projected Bool with `$p`, rather than the physical Uint64 source column. Using only source-column bindings therefore emits an incorrect inferred declaration or a wrong jOOQ field. ORDER BY resolution distinguishes direct physical/renamed projections from computed outputs using the existing parser contexts and token bindings; this small origin check is necessary even when names and types happen to match. Compound expressions over renamed/computed output aliases receive an actionable diagnostic until inference can represent their scope; direct output ordering remains supported without a new intermediate model or runtime scope framework.

`TestLiveYDBSharedExpressions` passed against the already-running `ydbplatform/local-ydb:26.3.1.16` (`sha256:32687d3bc4b7a3e4200e2142800e5fc2e91d48ba46160ea094e9f1ce56794c12`) using Go SDK v3.151.1 through generated native Query SDK and database/sql clients. Metadata comparisons and actual execution covered optional Boolean/string expressions, empty/grouped/NULL COUNT_IF, integer/Bool casts and Uint32 narrowing boundaries, invalid JSON, timestamp conversions, fitting COALESCE fallbacks, UTC/Random/Version/NANVL types, implicit names and mixed-type collisions, and wildcard normalization with ORDER BY. Additional direct server probes covered all integer/Bool CAST widths, nonliteral COALESCE fallbacks, optional Tz result types and rejection of Utf8 zone arguments; those probes do not establish Tz decoding support in every output runtime. The test only created and removed its own tables and did not restart the shared service.

The same suite additionally verified the combined wildcard and collision-shift case on 2026-09-23: for a table with `za Utf8 NOT NULL` and `zb Uint64 NOT NULL`, authored `SELECT t.*, 1, 2 AS column1 FROM t` returned wire names `column1, column2, za, zb` with types `Int32, Int32, Utf8, Uint64` and positional values `2, 1, "after", 18446744073709551615`. The normalized explicit projection returned `za, zb, column2, column1`; its reanalyzed result metadata and both generated Go adapters decoded those values correctly. The test hardcodes and checks both raw and normalized server metadata independently, so agreement between normalization and analysis alone cannot hide a wrong order. This evidence distinguishes the original wildcard collision's lexical ordering from the explicit aliases inserted during normalization.

The suite's opt-in jOOQ subtest also passed on that image with jOOQ 3.21.0, dialect 2.0.0 and JDBC 2.4.1. It executed implicit output names with multiple ORDER BY keys, a grouped `COUNT(*) AS n` ordered by `n DESC`, explicit/implicit aliases, parenthesized output ordering, a computed Bool alias shadowing a physical Utf8 column, qualified physical columns, and collision-renamed outputs. Its normalized wildcard-collision query decoded the same Utf8, maximum Uint64 and Int32 values through jOOQ's typed row mapping. The subtest creates and drops its own uniquely named tables and runs after both Go adapters; it requires `SQLC_YDB_TEST_MAVEN` in addition to `YDB_CONNECTION_STRING`.

The checked-in authors scenarios also passed on that server in both Go profiles and jOOQ 3.21.0 with dialect 2.0.0 and JDBC 2.4.1. They exercise prefix filtering, nullable/empty/nonempty bios, empty/nonempty conditional statistics, unaliased CAST results, and export metadata with a fitting Uint32 fallback. Date and Datetime are explicitly cast to String in the SQL example because not every output runtime supports those native result types.

## Non-correlated IN subqueries

The [YQL IN reference](https://ydb.tech/docs/en/yql/reference/syntax/expressions#in) documents membership against a nested SELECT. On 2026-09-23, direct QueryService probes against the already-running `ydbplatform/local-ydb:26.3.1.16` (`sha256:32687d3bc4b7a3e4200e2142800e5fc2e91d48ba46160ea094e9f1ce56794c12`) accepted scalar membership and a tuple left operand against one tuple-valued SELECT projection, including a declared `List<Struct<...>>` passed through AS_TABLE. A SELECT projecting multiple columns was rejected with `expecting single column table source`; mismatched tuple arity and incompatible component types were also rejected. Inner aliases can reuse outer names, but references to unavailable outer relations or columns are rejected rather than correlated. A separate JOIN ON conjunction containing membership was rejected with `JOIN ON expression must be a conjunction of equality predicates`; successful WHERE membership does not establish that JOIN ON form.

The same probes confirmed three-valued membership semantics: matching a non-null key returns true; a nonmatching key against a set containing NULL returns NULL; NULL against a nonempty set returns NULL; NULL against an empty set returns false. A NULL-only left and right expression is accepted and yields `Optional<Bool>`. Empty lists and filtered-empty subqueries select no rows with IN; NOT IN over an empty set includes rows with null left values.

A separate raw probe exposed a server filtering discrepancy on that image: with `records(id Uint64 NOT NULL, label Utf8 NOT NULL, PRIMARY KEY(id))` containing `(1,"x"),(2,"y"),(3,"wrong")` and a right-side table containing `(1,"x"),(2,"wrong")`, `WHERE (r.id,r.label) IN (SELECT (k.id,k.label) FROM selected AS k)` returned both rows 1 and 2 instead of row 1 alone. Bound and local AS_TABLE sources reproduced it, as did UPDATE; projection of the membership expression returned the expected Boolean values. Using the full composite primary key `(id,label)` or two non-key tuple components with a separate primary key produced the expected filtered rows. This is an observed version-specific discrepancy, not an established root cause or a client-side semantic policy. The generator preserves the original predicate without an automatic rewrite.

`TestLiveYDBInSubqueries` passed sequentially through generated native Go and database/sql clients with SDK v3.151.1 on that image. It verifies scalar/tuple membership, empty and duplicate batches, null-containing scalar sets, maximum Uint64, scoped aliases, physical-table right sides, complete composite-key UPDATE/DELETE, nullable composite keys against required tuple inputs, result metadata and raw server rejection of invalid or correlated forms. Its opt-in jOOQ subtest passed with jOOQ 3.21.0, dialect 2.0.0 and JDBC 2.4.1: scalar typed DSL reads, nested membership, same-named aliases, mixed numeric types, inner ordering/aggregation, UPDATE and DELETE RETURNING, plus a declared tuple read over non-key fields with RenderMapping and a second-component mismatch. Undeclared tuple subqueries remain outside the jOOQ DSL subset; the declared JDBC route retains the authored tuple projection. All tests create and drop only their own uniquely named tables without restarting the shared service.

The checked-in booktest examples also passed sequentially through both generated Go adapters on the same image. They check author filtering by recent books, all-non-key tuple membership that distinguishes book types belonging to the same author, empty results, and deletion by an author-name subquery while retaining unmatched books. Existing example table names were checked to be absent before the run; successful creation established ownership for cleanup.
